# コアの更新

配布するコアは、検証した版に固定します。ゲーム起動時にGitHubから最新版を取得したり、利用者の端末でコンパイルしたりする仕組みではありません。

## 更新候補を調べる

GitHubの **Actions → Check upstream core update → Run workflow** で実行します。
commitを空欄にすると、作者の`rom64`ブランチの最新コミットを取得します。以後の処理では取得したコミットを固定します。特定の版を調べる場合は40文字のコミットSHAを指定できます。

次の処理を自動で行います。

1. 固定したEmscriptenでWASMをビルドする。
2. コンパイルに使ったソース、ビルド入力、著作権・ライセンス表記を集める。
3. ROM・BIOS・認証情報などの混入を検査する。
4. 集めたソースから再ビルドし、JS・WASMが一致するか確認する。
5. 自作のテストプログラムで64MiB領域の読み取り、旧ステートの読み込み、セーブの保持を確認する。拡張フラッシュと追加RAMを持つ版では、それらの保存も確認する。

結果は`core-update-review`の`latest-report.json`に出ます。`needs-review`は機械検査の通過、`blocked`は検査失敗を意味します。どちらも公開済みのコアを変更しません。ROM容量の上限も変更しません。

**ライセンスの変更は人による確認が必要です。** ルートのLICENSEが同じでも、新しい依存コードやファイル内の権利表記が増える場合があります。レポートにはソース全体の変更ファイル一覧と比較リンクを残します。公開リポジトリのActionsでも、未審査のバイナリや作者のリポジトリ全体を成果物として配布しません。アップロードするのは検査結果だけです。

## 手元で候補をビルドする

`sources/mgba-web-port/upstream.json`に指定したemsdkを用意し、Emscripten 4.0.15をインストール・有効化します。CMake 3.31.6とNinja 1.11.1をPATHに追加し、リポジトリ直下で実行します。

```sh
python web/scripts/core-candidate.py --emsdk /path/to/emsdk
# 特定のコミットを再検証するとき
python web/scripts/core-candidate.py --emsdk /path/to/emsdk --commit <40文字のSHA>
```

候補、再ビルド用ソース、ビルドログはGit管理外の`work/core-candidates/`へ保存されます。既存の候補を上書きしません。スクリプトは公開されている上流ソースと自作テストだけを使い、利用者のROM・セーブを読み込みません。

## 配布版への反映

候補を採用するときは、変更されたライセンス・依存関係を確認し、対応ソース、変更履歴、クレジットを同じリリースに揃えます。旧ステートの互換性が確認できない変更では、互換性IDと保存先を分け、既存データを上書きしません。ビルド成功だけでは実際のゲームすべての互換性は確認できません。

128MiBなど新しい容量への対応は、コアの読み取り方式に合わせたテスト、Web側の容量制限、メモリ使用量、保存・復旧の確認が必要です。容量だけを自動で引き上げません。

ブラウザ・オフライン・通信の回帰テストを通し、`SOURCES.json`、ソース配布物、`RELEASE_CONTENT.json`、`RELEASE_REVIEW.json`を更新します。その後、既存の検証CIとPagesの公開手順へ進みます。クレジットだけでライセンス上の義務を満たしたものとは扱いません。

このワークフローは手動起動です。定期実行や自動マージ・自動公開は有効にしていません。

## 0.3.3で採用する更新

rom64の `0ba86121bd92aa570d38301086d8e8f584238d62` を採用。6MiBの拡張セーブ、16MiBの追加RAM、フラッシュ書き込みの高速化に対応します。Web側のセーブ上限はRTC情報を含めて6MiB＋16バイト、ステート上限は32MiBに変更しました。ROM上限は64MiBのままです。

CPUのオーバークロック設定は1倍に固定し、従来の速度を維持します。Qt版の自動バックアップはWeb用ビルドに含まれません。Web側では従来の端末内バックアップを継続します。対応ソースと128件のコンパイル対象の権利表記を照合し、配布ソースだけからの再ビルドでJS・WASMの一致を確認しました。
